# 模板数据模式与多 SQL 查询设计

**日期**：2026-09-21  
**状态**：设计稿 v2，已完成首轮代码级审阅  
**适用仓库**：`xdguo-design/print-platform`  
**适用范围**：模板数据配置、JSON/SQL 测试取数、预览、模拟打印/插件测试、测试记录  
**不包含**：正式业务规则、任意 SQL 执行、正式打印任务状态机重构、运营报表口径重构

---

## 1. 背景

当前模板草稿和发布版本保存：

- `design`
- `sampleData`

其中 `sampleData` 同时承担模板字段校验和样例预览数据。现有平台已经具备：

- 模板草稿、测试、审核、发布、回滚和不可变发布版本；
- 多数据库连接配置与连接测试；
- 模板变量和动态表格校验；
- 浏览器预览/打印、浏览器扩展与本地 Print Agent 链路；
- 正式打印任务、数据快照、打印尝试和运营报表。

本设计在现有模型上增加统一 `dataConfig`，让模板明确选择 JSON 或 SQL 数据模式，并让 SQL 查询配置跟随模板版本整体发布和回滚。

核心原则：

1. **模板数据配置随模板版本存储。**
2. **SQL 查询不是独立版本对象。**
3. **发布版本不可变；回滚时设计、样例数据和查询配置一起回滚。**
4. **模板继续只绑定最终渲染 JSON，不感知 SQL。**
5. **测试执行与正式打印记录分离。**
6. **数据库账号只读是第一层安全边界，平台校验和超时/行数限制是第二层。**
7. **连接凭据只由后端解析，前端和模板 JSON 不保存密码。**

---

## 2. 目标

本期实现以下能力：

- 模板支持 `JSON` 与 `SQL` 两种数据模式。
- JSON 模式继续使用模板样例 JSON 预览，并允许测试时提交一份临时 JSON 数据。
- SQL 模式允许同一模板配置多条有序查询。
- 每条查询可以选择不同的已配置数据连接。
- SQL 使用命名参数，不允许字符串拼接业务参数。
- 每条查询有稳定的 `queryId`、结果键 `resultKey` 和结果格式 `resultType`。
- 多条查询结果合并成统一渲染数据，例如：
  ```json
  {
    "order": {},
    "items": [],
    "summary": {}
  }
  ```
- SQL 取数结果可直接用于模板预览、模拟打印和插件测试。
- 测试记录保存模板版本、数据模式、每条查询状态/耗时、渲染结果和打印方式。
- 测试记录不进入正式打印运营报表。
- 失败时不使用半成品数据继续渲染或打印。

---

## 3. 非目标

本期明确不做：

- 不允许用户在打印时临时输入任意 SQL。
- 不把 SQL 查询拆成独立的“查询模板/查询版本”产品。
- 不在打印平台内实现收费、退费、库存结算、金额计算等业务规则。
- 不支持 SQL 写操作。
- 不支持存储过程、匿名代码块、多语句脚本。
- 不在模板配置里保存数据库密码、Token 或 Secret。
- 不改变正式 `print_task` 的任务状态机。
- 不把测试数据混入正式 `print_task / print_attempt / report`。
- 不保证不同数据库 SQL 方言完全一致；SQL 内容由模板维护者针对所选连接负责。
- 不在本期增加复杂 ETL、跨查询 JOIN DSL 或表达式脚本。

## 4. 总体模型

### 4.1 模板数据结构扩展

现有：

```text
print_template
  design_json
  sample_data_json

print_template_version
  design_json
  sample_data_json
```

扩展为：

```text
print_template
  design_json
  sample_data_json
  data_config_json

print_template_version
  design_json
  sample_data_json
  data_config_json
```

`data_config_json` 与 `design_json`、`sample_data_json` 同步进入版本快照。

不单独建立 `template_query_version` 表。

### 4.2 dataConfig 顶层结构

```json
{
  "schemaVersion": 1,
  "mode": "SQL",
  "queries": []
}
```

字段：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| schemaVersion | integer | 是 | 数据配置结构版本，本期固定为 1 |
| mode | enum | 是 | `JSON` 或 `SQL` |
| queries | array | SQL 模式必填 | 有序查询列表；JSON 模式必须为空或省略 |

### 4.3 JSON 模式

推荐配置：

```json
{
  "schemaVersion": 1,
  "mode": "JSON",
  "queries": []
}
```

规则：

- 模板设计器默认使用 `sampleData` 预览。
- 测试接口可传入 `inputData` 覆盖样例数据。
- `inputData` 只用于当前测试，不写回模板。
- 发布前字段校验仍以模板自身 `sampleData` 为基准。
- 正式打印由业务系统直接传数据时，仍需生成不可变 `print_snapshot`。

### 4.4 SQL 模式

示例：

```json
{
  "schemaVersion": 1,
  "mode": "SQL",
  "queries": [
    {
      "queryId": "order-header",
      "name": "采购订单主表",
      "connectionId": "ds-erp",
      "sql": "SELECT order_no, supplier_name, order_date, total_amount FROM purchase_order WHERE id = :orderId",
      "params": [
        {
          "name": "orderId",
          "type": "STRING",
          "required": true
        }
      ],
      "resultKey": "order",
      "resultType": "OBJECT",
      "order": 10,
      "enabled": true
    },
    {
      "queryId": "order-items",
      "name": "采购订单明细",
      "connectionId": "ds-erp",
      "sql": "SELECT product_code, product_name, qty, unit_price, amount FROM purchase_order_item WHERE order_id = :orderId ORDER BY line_no",
      "params": [
        {
          "name": "orderId",
          "type": "STRING",
          "required": true
        }
      ],
      "resultKey": "items",
      "resultType": "ARRAY",
      "order": 20,
      "enabled": true
    }
  ]
}
```

## 5. 查询配置数据结构

### 5.1 QueryConfig

```text
QueryConfig
- queryId: string
- name: string
- connectionId: string
- sql: string
- params: QueryParam[]
- resultKey: string
- resultType: OBJECT | ARRAY | SCALAR
- order: integer
- enabled: boolean
- timeoutMs?: integer
- maxRows?: integer
```

建议 JSON：

```json
{
  "queryId": "visit-fee-items",
  "name": "门诊费用明细",
  "connectionId": "ds-his-readonly",
  "sql": "SELECT item_name, spec, qty, unit_price, amount FROM outpatient_fee_item WHERE visit_no = :visitNo ORDER BY seq_no",
  "params": [
    {
      "name": "visitNo",
      "type": "STRING",
      "required": true
    }
  ],
  "resultKey": "items",
  "resultType": "ARRAY",
  "order": 20,
  "enabled": true,
  "timeoutMs": 3000,
  "maxRows": 1000
}
```

### 5.2 queryId

`queryId` 是查询的稳定技术标识。

约束：

- 同一模板内唯一。
- 发布后随版本不可变。
- 修改查询名称不修改 `queryId`。
- 测试记录通过 `queryId` 关联，不通过展示名称关联。
- 建议格式：`[a-z][a-z0-9-]{1,63}`。

### 5.3 QueryParam

```text
QueryParam
- name: string
- type: STRING | INTEGER | DECIMAL | BOOLEAN | DATE | DATETIME
- required: boolean
- defaultValue?: scalar
```

本期不支持数组参数和动态 SQL 片段。

参数必须使用后端 PreparedStatement/NamedParameter 绑定，禁止把参数值拼接进 SQL 字符串。

### 5.4 resultKey

`resultKey` 决定查询结果写入最终渲染 JSON 的位置。

本期只允许顶层键：

```text
order
items
summary
patient
visit
operator
...
```

不支持：

```text
order.items.detail
items[0]
__proto__
constructor
prototype
```

约束：

- 同一模板内唯一。
- 格式建议：`[A-Za-z_][A-Za-z0-9_]{0,63}`。
- 保留键 `__proto__`、`prototype`、`constructor` 禁止使用。

### 5.5 resultType

#### OBJECT

- 允许返回 0 或 1 行。
- 0 行 => `null`。
- 超过 1 行 => 查询失败，错误码 `RESULT_CARDINALITY_MISMATCH`。

#### ARRAY

- 返回行数组。
- 0 行 => `[]`。
- 受 `maxRows` 限制。

#### SCALAR

- 允许返回 0 或 1 行。
- 返回第一行第一列。
- 0 行 => `null`。
- 超过 1 行 => 查询失败。

### 5.6 order

执行顺序按：

```text
order ASC, queryId ASC
```

首期按顺序串行执行，不做并发查询。

原因：

- 控制业务数据库瞬时压力；
- 测试日志顺序稳定；
- 便于定位失败查询；
- 为以后增加依赖查询保留空间。

当前查询之间不能引用前一查询结果，只能共享测试输入参数。

## 6. 最终渲染数据

SQL 模式执行成功后，后端按照 `resultKey` 合并：

```json
{
  "order": {
    "order_no": "PO202609210001",
    "supplier_name": "示例供应商",
    "order_date": "2026-09-21",
    "total_amount": 1280.50
  },
  "items": [
    {
      "product_code": "P001",
      "product_name": "示例商品",
      "qty": 2,
      "unit_price": 100,
      "amount": 200
    }
  ]
}
```

模板继续使用现有绑定：

```text
{{order.order_no}}
{{order.supplier_name}}

TABLE binding = items
```

设计器、分页器和渲染器不需要知道这些数据来自 SQL。

## 7. 数据库表设计

### 7.1 print_template

新增：

```sql
data_config_json TEXT NOT NULL DEFAULT '{"schemaVersion":1,"mode":"JSON","queries":[]}'
```

### 7.2 print_template_version

新增：

```sql
data_config_json TEXT NOT NULL DEFAULT '{"schemaVersion":1,"mode":"JSON","queries":[]}'
```

发布时保存：

```text
design_json
sample_data_json
data_config_json
```

回滚时从目标版本复制三者，生成新的发布版本，不修改历史版本。

### 7.3 template_test_run

新增测试主表：

```sql
CREATE TABLE template_test_run (
  id TEXT PRIMARY KEY,
  template_id TEXT NOT NULL,
  template_version INTEGER,
  draft_revision INTEGER,
  data_mode TEXT NOT NULL,
  test_type TEXT NOT NULL,
  status TEXT NOT NULL,
  input_params_json TEXT,
  input_data_json TEXT,
  render_data_json TEXT,
  render_status TEXT,
  print_channel TEXT,
  print_status TEXT,
  printer_id TEXT,
  message TEXT,
  started_at TEXT NOT NULL,
  finished_at TEXT,
  elapsed_ms INTEGER,
  FOREIGN KEY(template_id) REFERENCES print_template(id)
);
```

说明：

- 测试草稿时记录 `draft_revision`。
- 测试已发布版本时记录 `template_version`。
- 二者至少有一个。
- `render_data_json` 用于复盘测试，不进入正式 `print_snapshot`。
- 如测试数据含敏感字段，后续可增加留存策略；本期默认仅限平台管理员/模板人员查看。

### 7.4 template_test_query

新增查询明细表：

```sql
CREATE TABLE template_test_query (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  test_run_id TEXT NOT NULL,
  query_id TEXT NOT NULL,
  query_name TEXT NOT NULL,
  connection_id TEXT NOT NULL,
  result_key TEXT NOT NULL,
  result_type TEXT NOT NULL,
  status TEXT NOT NULL,
  row_count INTEGER,
  elapsed_ms INTEGER,
  error_code TEXT,
  error_message TEXT,
  started_at TEXT NOT NULL,
  finished_at TEXT,
  FOREIGN KEY(test_run_id) REFERENCES template_test_run(id)
);
```

不保存：

- 数据库密码；
- Secret 内容；
- 带真实参数值展开后的完整 SQL。

测试记录可以保存参数 JSON，但日志展示需按字段策略脱敏。

## 8. API 契约

接口继续归属模板域；查询配置不是独立发布资源。除模板创建外，本期不要求为查询配置单独提供 CRUD API，查询配置随 \`PUT /api/templates/{id}/draft\` 一起保存。

### 8.1 通用目标版本选择

测试类接口统一使用：

\`\`\`json
{
  "versionNo": null
}
\`\`\`

语义：

- \`versionNo=null\` 或省略：使用数据库中当前已保存草稿，并在测试记录中固化当时的 \`draftRevision\`。
- \`versionNo=N\`：使用 \`print_template_version.version_no=N\` 的不可变版本。
- 测试接口不接受客户端直接提交 \`design/dataConfig\` 作为执行配置；前端应先保存草稿，再发起测试。
- 响应必须回显实际解析目标，防止用户误以为测试的是另一个版本。

统一目标对象：

\`\`\`json
{
  "target": {
    "kind": "DRAFT",
    "draftRevision": 7,
    "versionNo": null
  }
}
\`\`\`

或：

\`\`\`json
{
  "target": {
    "kind": "VERSION",
    "draftRevision": null,
    "versionNo": 3
  }
}
\`\`\`

### 8.2 保存草稿

现有接口：

\`\`\`http
PUT /api/templates/{id}/draft
\`\`\`

请求扩展：

\`\`\`json
{
  "name": "采购订单",
  "design": {},
  "sampleData": {},
  "dataConfig": {
    "schemaVersion": 1,
    "mode": "SQL",
    "queries": []
  }
}
\`\`\`

兼容规则：

- \`design\`、\`sampleData\` 继续保持现有必填规则。
- \`dataConfig\` 对兼容旧客户端允许为空。
- 已存在模板收到 \`dataConfig=null\` 时保留原值，不覆盖。
- 新模板默认写入 \`{"schemaVersion":1,"mode":"JSON","queries":[]}\`。
- 新前端必须始终显式提交 \`dataConfig\`。
- 保存成功继续返回完整 \`PrintTemplate\`，其中包含 \`dataConfig\`。

### 8.3 获取模板与版本

保留：

\`\`\`http
GET /api/templates/{id}
GET /api/templates/{id}/versions
\`\`\`

\`PrintTemplate\` 和 \`PrintTemplateVersion\` 均增加 \`dataConfig\`。历史版本读取到缺失列/旧数据时由 Repository 映射为默认 JSON 配置，不把 \`null\` 暴露给前端。

### 8.4 模板静态校验

保留：

\`\`\`http
GET /api/templates/{id}/validate
\`\`\`

响应结构保持兼容：

\`\`\`json
{
  "valid": false,
  "errors": ["查询 order-header 使用的数据连接不存在"],
  "warnings": ["查询 order-items 的 order 与其他查询重复"]
}
\`\`\`

该接口只做静态校验，不连接业务数据库、不执行 SQL。

### 8.5 单查询测试

新增：

\`\`\`http
POST /api/templates/{id}/queries/{queryId}/test
Content-Type: application/json
\`\`\`

请求：

\`\`\`json
{
  "versionNo": null,
  "params": {
    "orderId": "10001"
  }
}
\`\`\`

约束：

- 仅 SQL 模式可调用。
- \`queryId\` 必须存在且 enabled。
- 仅执行指定查询，不执行其他查询，不进入模板渲染。
- 创建 \`testType=QUERY\` 的独立测试记录。

成功响应：

\`\`\`json
{
  "testRunId": "TR-01H...",
  "status": "SUCCESS",
  "target": {
    "kind": "DRAFT",
    "draftRevision": 7,
    "versionNo": null
  },
  "query": {
    "queryId": "order-header",
    "name": "采购订单主表",
    "resultKey": "order",
    "resultType": "OBJECT",
    "rowCount": 1,
    "elapsedMs": 32
  },
  "result": {
    "orderNo": "PO202609210001"
  }
}
\`\`\`

查询已经开始执行但出现数据库错误、超时、结果形状错误时，HTTP 仍返回 \`200\`，并返回持久化后的失败测试结果：

\`\`\`json
{
  "testRunId": "TR-01H...",
  "status": "FAILED",
  "error": {
    "code": "QUERY_TIMEOUT",
    "message": "查询执行超时"
  }
}
\`\`\`

这样测试失败本身是可查询的业务结果，而不是丢失为未记录的 HTTP 异常。

### 8.6 获取测试数据并准备预览

新增：

\`\`\`http
POST /api/templates/{id}/test-data
\`\`\`

请求：

\`\`\`json
{
  "versionNo": null,
  "params": {
    "orderId": "10001"
  },
  "inputData": null
}
\`\`\`

规则：

- JSON 模式允许 \`inputData\`；为空时使用模板 \`sampleData\`。
- SQL 模式拒绝非空 \`inputData\`，只允许 \`params\`。
- SQL 模式执行全部 enabled 查询并合并结果。
- 该接口负责“解析数据”，不伪装成后端渲染器；当前项目实际 HTML 渲染发生在 Vue 前端。
- 接口创建 \`testType=PREVIEW\` 测试记录，数据解析成功后保持 \`RUNNING\`，等待前端回写渲染结果。

数据准备成功响应：

\`\`\`json
{
  "testRunId": "TR-01H...",
  "status": "RUNNING",
  "dataMode": "SQL",
  "target": {
    "kind": "DRAFT",
    "draftRevision": 7,
    "versionNo": null
  },
  "templateSnapshot": {
    "templateId": "TPL-1234",
    "code": "purchase-order",
    "name": "采购订单",
    "documentType": "FORM",
    "design": {}
  },
  "renderData": {
    "order": {},
    "items": []
  },
  "queries": [
    {
      "queryId": "order-header",
      "status": "SUCCESS",
      "rowCount": 1,
      "elapsedMs": 32
    }
  ],
  "renderStatus": "NOT_STARTED",
  "elapsedMs": 61
}
\`\`\`

返回 \`templateSnapshot.design\` 的原因：测试历史发布版本时，不能错误使用当前草稿的 design 进行预览。

### 8.7 前端渲染结果回写

新增：

\`\`\`http
POST /api/template-test-runs/{testRunId}/render-result
\`\`\`

请求：

\`\`\`json
{
  "success": true,
  "pageCount": 2,
  "elapsedMs": 14,
  "message": "预览渲染成功"
}
\`\`\`

规则：

- PREVIEW 测试在该回写成功后才进入终态。
- \`success=true\`：\`render_status=SUCCESS\`，若不需要打印则 test run => \`SUCCESS\`。
- \`success=false\`：\`render_status=FAILED\`，test run => \`FAILED\`。
- 同一终态重复回写相同结果按幂等成功处理；冲突结果返回 \`409\`。
- 长时间没有回写的 RUNNING 记录由后续清理机制标为 FAILED，错误码 \`CLIENT_CALLBACK_TIMEOUT\`。

### 8.8 模拟打印测试

新增：

\`\`\`http
POST /api/templates/{id}/tests/simulated-print
\`\`\`

请求与 \`test-data\` 相同。服务端只负责固化测试目标、解析数据、创建 \`SIMULATED_PRINT\` 测试记录，并返回 \`templateSnapshot + renderData + testRunId\`。

## 9. SQL 安全规则

### 9.1 连接级规则

执行 SQL 的数据连接必须：

- `enabled=true`
- `readOnly=true`
- Secret 可由后端 `secretRef` 正常解析

任何一项不满足都拒绝执行。

### 9.2 账号权限

推荐数据库账号本身只授予：

```text
SELECT / VIEW READ
```

不得仅依赖 JDBC `setReadOnly(true)`。

### 9.3 SQL 类型

本期仅允许单条只读查询。

允许的起始类型：

- `SELECT`
- 可证明最终为 SELECT 的 `WITH ... SELECT`

禁止：

- INSERT
- UPDATE
- DELETE
- MERGE
- UPSERT
- REPLACE
- CREATE
- ALTER
- DROP
- TRUNCATE
- GRANT
- REVOKE
- CALL
- EXEC / EXECUTE
- COPY
- LOAD
- ATTACH / DETACH
- PRAGMA 写操作
- SELECT ... INTO
- FOR UPDATE
- 多语句

SQL 校验必须在后端执行。

仅使用关键词正则不足以作为最终安全措施；实现时应至少结合：

1. 单语句解析；
2. 顶层语句类型检查；
3. 禁止语法节点检查；
4. 只读数据库账号；
5. JDBC readOnly；
6. 超时和返回限制。

### 9.4 参数规则

- SQL 中出现的所有命名参数必须在 `params` 定义。
- `params` 定义但 SQL 未引用 => warning。
- 测试输入包含未定义参数 => error。
- required 参数缺失 => error。
- 类型转换失败 => error。
- 参数名格式：`[A-Za-z_][A-Za-z0-9_]{0,63}`。
- 同一查询参数名唯一。

### 9.5 超时

平台配置：

```text
defaultQueryTimeoutMs = 5000
maxQueryTimeoutMs = 30000
```

模板可配置 `timeoutMs`，但必须：

```text
100 <= timeoutMs <= maxQueryTimeoutMs
```

不配置则使用平台默认值。

### 9.6 行数

平台配置：

```text
defaultMaxRows = 1000
hardMaxRows = 10000
```

模板 `maxRows` 不能超过 `hardMaxRows`。

执行时应设置 JDBC maxRows；同时在结果映射层再次检查。

### 9.7 查询失败策略

任意 enabled 查询失败：

- 当前查询记 `FAILED`；
- 后续未执行查询记 `SKIPPED`；
- 整个 test run 记 `FAILED`；
- 不进入模板渲染；
- 不发起模拟打印或插件打印。

首期不提供 `optional query`。

## 10. 模板校验规则

现有设计/绑定校验继续保留，在其前增加数据配置校验。

### 10.1 通用校验

错误：

- `dataConfig` 不是对象；
- `schemaVersion != 1`；
- mode 不是 `JSON | SQL`。

### 10.2 JSON 模式

错误：

- queries 存在 enabled 查询。

警告：

- sampleData 为空对象且模板存在变量绑定。

### 10.3 SQL 模式

错误：

- queries 为空；
- 没有 enabled 查询；
- queryId 缺失或重复；
- queryId 格式错误；
- connectionId 缺失；
- 数据连接不存在；
- 数据连接 disabled；
- 数据连接 readOnly=false；
- SQL 为空；
- SQL 非只读；
- SQL 为多语句；
- resultKey 缺失或重复；
- resultKey 非法；
- resultType 非法；
- order 非整数；
- timeoutMs/maxRows 超范围；
- 参数定义重复或非法；
- SQL 参数没有定义；
- sampleData 中不存在模板依赖的最终字段。

警告：

- 查询定义参数但 SQL 未使用；
- 多条查询 order 相同；
- SQL 模式 sampleData 与声明的 resultKey 结构不一致；
- ARRAY 对应 sampleData 不是数组；
- OBJECT 对应 sampleData 不是对象/null；
- SCALAR 对应 sampleData 是对象或数组。

### 10.4 sampleData 仍然必需

即使 SQL 模式，`sampleData` 仍保留且建议必填。

原因：

- 设计器离线/不连业务库也可以编辑；
- 发布前可以静态验证绑定；
- 模板中心列表预览不必执行 SQL；
- 数据源不可用时仍可检查版式；
- 第一批内置模板需要稳定 JSON 示例。

SQL 查询结果结构必须与 sampleData 对齐，而不是用数据库实时结果替代模板契约。

## 11. 测试执行流程

### 11.1 JSON 预览

\`\`\`text
创建 template_test_run
→ 选择草稿/发布版本
→ 取 inputData（有则使用）或 sampleData
→ 返回 templateSnapshot + renderData
→ 前端 PreviewModal 使用 renderData 渲染
→ 回写 render-result
→ test run 终态
\`\`\`

### 11.2 SQL 预览

\`\`\`text
创建 template_test_run
→ 静态校验 dataConfig
→ 校验连接和参数
→ 顺序执行 QueryConfig
→ 实时写 template_test_query 状态
→ 按 resultKey 合并 renderData
→ 返回 templateSnapshot + renderData
→ 前端 PreviewModal 使用 renderData 渲染
→ 回写 render-result
→ test run 终态
\`\`\`

### 11.3 模拟打印

\`\`\`text
准备测试数据
→ 前端用现有分页器 + buildPrintDocument 生成打印 HTML
→ 不调用实体打印机
→ POST print-result(channel=SIMULATED)
\`\`\`

### 11.4 插件测试

\`\`\`text
准备测试数据
→ 前端生成打印 HTML
→ window.postMessage PRINT
→ Browser Extension
→ Local Print Agent /print
→ Agent accepted/result
→ POST print-result(channel=BROWSER_EXTENSION_AGENT)
\`\`\`

现阶段 Agent 为 mock，只能证明链路可达和请求被接受，不能把 accepted 等同于实体打印成功。

### 11.5 平台数据库事务边界

当前平台 SQLite 连接池 \`maximum-pool-size=1\`。测试服务不得用一个长 \`@Transactional\` 包住外部 SQL 查询全过程。

必须采用短事务：创建测试记录后释放平台 SQLite 连接；外部查询在平台事务外执行；每条查询完成后用短事务更新状态；最后短事务更新 test run。否则慢业务 SQL 会占住唯一平台数据库连接，阻塞其他功能。

### 11.6 同一数据连接的一致性

同一个 test run 内，相同 \`connectionId\` 的查询优先复用同一只读 JDBC Connection；数据库支持时使用同一只读事务，减少主表/明细查询间的数据漂移。不同 \`connectionId\` 之间不提供分布式事务或全局一致性保证。

## 12. 正式打印边界

本设计的测试执行器与以后正式 SQL 打印可以复用同一个 `TemplateDataResolver`，但正式打印必须多一步：

```text
resolve data
→ freeze immutable payload
→ create print_snapshot
→ create/queue print_task
→ print
```

必须保证：

- 重试不重新查业务数据库；
- 换机不重新查业务数据库；
- 重打是否复用原快照由业务动作定义，但同一任务的 retry 必须复用原快照；
- 模板版本与快照可追溯。

本期如果只实现模板测试，不需要立刻把正式任务创建 API 改为 SQL 取数。

## 16. 兼容与迁移

### 16.1 老模板默认值

老模板统一映射为：

\`\`\`json
{
  "schemaVersion": 1,
  "mode": "JSON",
  "queries": []
}
\`\`\`

现有模板行为不变。

### 16.2 不能只改 schema.sql

当前工程通过 Spring SQL init 执行 \`db/schema.sql\`，主要是 \`CREATE TABLE IF NOT EXISTS\`，没有 Flyway/Liquibase。因此仅在原建表 SQL 中增加 \`data_config_json\` 不能给已有 SQLite 文件增加列。

本期必须增加幂等 schema migration：

- 启动时通过 JDBC \`DatabaseMetaData\` 检查 \`print_template.data_config_json\`；
- 缺失时执行 \`ALTER TABLE ... ADD COLUMN ...\`；
- 对 \`print_template_version\` 同样处理；
- 新建 \`template_test_run/template_test_query\` 仍可由 \`schema.sql\` 幂等创建；
- 增加集成测试：先建立“旧 schema 数据库”，再启动新版本并验证列自动补齐且旧模板可读取。

不得要求用户手工删除 \`print-platform.db\` 作为升级方案。

### 16.3 老 API

\`PUT /api/templates/{id}/draft\` 未传 \`dataConfig\` 时：

\`\`\`text
request.dataConfig != null
  ? validate + replace
  : keep existing dataConfig
\`\`\`

新前端始终传 \`dataConfig\`。

### 16.4 历史发布版本

迁移后已有 \`print_template_version\` 行的 \`data_config_json\` 使用默认 JSON 配置。Repository 层仍做防御性 fallback，避免异常数据返回 null。

### 16.5 导入导出兼容

当前模板导入/导出只包含 \`name/design/sampleData\`。本期扩展为：

\`\`\`json
{
  "name": "...",
  "design": {},
  "sampleData": {},
  "dataConfig": {}
}
\`\`\`

导入旧 JSON 文件缺少 \`dataConfig\` 时按 JSON 默认模式处理。

## 17. 错误码与结果约束

建议错误码：

\`\`\`text
DATA_CONFIG_INVALID
DATA_MODE_NOT_SUPPORTED
QUERY_CONFIG_INVALID
QUERY_NOT_FOUND
QUERY_DISABLED
QUERY_DUPLICATE_ID
RESULT_KEY_DUPLICATE
DATA_SOURCE_NOT_FOUND
DATA_SOURCE_DISABLED
DATA_SOURCE_NOT_READ_ONLY
SECRET_NOT_RESOLVED
SQL_NOT_READ_ONLY
SQL_MULTIPLE_STATEMENTS
SQL_PARAMETER_MISSING
SQL_PARAMETER_UNKNOWN
SQL_PARAMETER_TYPE_INVALID
QUERY_TIMEOUT
QUERY_MAX_ROWS_EXCEEDED
QUERY_RESULT_TOO_LARGE
QUERY_EXECUTION_FAILED
RESULT_CARDINALITY_MISMATCH
RESULT_SHAPE_MISMATCH
RESULT_DUPLICATE_COLUMN
RENDER_VALIDATION_FAILED
RENDER_FAILED
CLIENT_CALLBACK_TIMEOUT
PLUGIN_PRINT_FAILED
SIMULATED_PRINT_FAILED
\`\`\`

### 17.1 QueryParam 输入格式

| type | JSON 输入 |
|---|---|
| STRING | string |
| INTEGER | JSON integer |
| DECIMAL | JSON number 或十进制定点字符串；后端转 BigDecimal |
| BOOLEAN | true/false |
| DATE | \`YYYY-MM-DD\` |
| DATETIME | \`YYYY-MM-DDTHH:mm:ss[.SSS]\`，按业务库本地时间绑定 |

规则：

- required=true 且输入缺失且无 defaultValue => \`SQL_PARAMETER_MISSING\`；
- 非必填且无输入/默认值 => JDBC NULL；
- 请求中出现未在 enabled 查询定义的参数 => \`SQL_PARAMETER_UNKNOWN\`；
- 同名参数被多条 enabled 查询引用时，类型必须一致，defaultValue 冲突视为配置错误。

### 17.2 JDBC 结果映射

- JSON 字段名使用 JDBC \`ResultSetMetaData.getColumnLabel()\`，模板作者应使用 SQL alias 固定字段名。
- 同一结果行出现重复 column label => \`RESULT_DUPLICATE_COLUMN\`。
- SQL NULL => JSON null。
- DATE/TIME/TIMESTAMP => ISO 字符串。
- DECIMAL/NUMERIC => JSON decimal number，内部使用 BigDecimal。
- BLOB/二进制大对象首期不支持。

SCALAR 额外要求：结果必须恰好 1 列；多列 => \`RESULT_SHAPE_MISMATCH\`。

### 17.3 maxRows 实现

不能仅调用 \`Statement.setMaxRows(maxRows)\` 后静默截断。实现应读取 \`maxRows + 1\`：结果不超过 maxRows 才成功；超过则 \`QUERY_MAX_ROWS_EXCEEDED\`。OBJECT/SCALAR 为检测多行至少读取 2 行。

### 17.4 timeoutMs 实现

标准 JDBC \`Statement#setQueryTimeout\` 以秒为单位。保留 \`timeoutMs\` 配置字段，执行器应：

- \`setQueryTimeout(ceil(timeoutMs / 1000))\`；
- 同时记录 wall-clock 时间；
- 超时后尝试 \`Statement.cancel()\` 并关闭连接；
- 对外统一映射为 \`QUERY_TIMEOUT\`。

### 17.5 错误信息脱敏

## 20. 实施边界与审阅结论

本设计决定：

1. **采用模板 JSON 配置，不单建查询版本表。**
2. **dataConfig 同时存在于草稿和不可变发布版本。**
3. **SQL 查询配置跟随模板版本发布和回滚。**
4. **queryId 是稳定技术 ID，name 仅用于展示。**
5. **SQL 查询结果只负责生成最终 JSON；模板绑定层不感知数据库。**
6. **测试记录独立于正式 print_task 和运营报表。**
7. **SQL 模式仍保留 sampleData 作为模板数据契约和设计期数据。**
8. **任何 enabled 查询失败即终止整次数据解析，不打印部分数据。**
9. **正式打印必须先冻结不可变数据快照，retry 不重新查询数据库。**
10. **首期不实现跨查询依赖、可选查询、动态 SQL、存储过程或写 SQL。**
11. **内置模板提供真实业务语义结构，但不会假定客户数据库表结构。**
12. **门诊普通业务票据不以“法定发票”命名。**

此设计通过审阅后，再进入代码实施。

## 21. 测试数据留存

门诊、交易和库存测试数据可能包含敏感业务数据。测试报表的必需信息是“版本、数据模式、查询状态/耗时、打印方式与结果”，不是长期保存完整业务 payload。

因此：

- \`template_test_run.input_data_json\`、\`render_data_json\` 保留为可选列；
- 默认配置 \`print.template-test.persist-payload=false\`；
- 默认只持久化执行元数据、行数、状态、错误码和耗时；
- 部署方明确开启 payload 留存时才保存 input/render data；
- 即使开启，也不得保存 Secret，参数展示按字段名策略脱敏；
- API 同步响应仍可把本次 \`renderData\` 返回给当前前端用于预览。

\`template_test_run\` 建议补充：

\`\`\`text
error_code
page_count
agent_job_id
payload_persisted
\`\`\`

\`print_status\` 增加 \`PENDING\`；\`test_type\` 增加 \`QUERY\`。

\`template_test_query\` 增加：

\`\`\`sql
UNIQUE(test_run_id, query_id)
CREATE INDEX idx_template_test_run_template_started
  ON template_test_run(template_id, started_at DESC);
CREATE INDEX idx_template_test_query_run
  ON template_test_query(test_run_id, id);
\`\`\`

## 22. Secret 解析契约

当前 \`data_source_connection\` 已保存 \`secretRef\`，但现有代码只有“连接测试时临时传 password”，没有用于模板 SQL 执行的 Secret Resolver。

本期必须实现：

\`\`\`text
SecretResolver
  resolve(secretRef) -> secret credential
\`\`\`

首期本地实现可支持环境变量引用，例如 \`env:ERP_DB_PASSWORD\`。

规则：

- \`secretRef\` 为空时允许无密码数据库；
- 不允许把解析出的 Secret 写入日志、模板 JSON、测试记录或 API 响应；
- SQL 测试 API 不接收临时 password 作为绕过；
- Secret 解析失败 => \`SECRET_NOT_RESOLVED\`；
- 后续可增加部署平台 Secret/KMS adapter，不改变 \`dataConfig\`。

## 23. 代码级审阅结论

本轮基于当前 \`main\` 的 Java/Vue/SQLite/扩展/Agent 实现审阅。设计方向可实施，但进入编码前必须按下表修正。

| 级别 | 发现 | 当前事实 | 实施要求 |
|---|---|---|---|
| P0 | 已有 SQLite 无法靠 schema.sql 自动加列 | 当前只有 \`CREATE TABLE IF NOT EXISTS\`，无迁移框架 | 增加幂等 schema migrator，并补旧库升级测试 |
| P0 | 预览硬编码 sampleData | \`PreviewModal\`、设计画布直接使用 \`template.sampleData/model.sampleData\` | \`PreviewModal\` 增加独立 \`renderData\`；SQL 测试结果必须走该数据 |
